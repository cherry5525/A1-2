# 🧳 국내 여행지 추천 프로그램 (Gemini + Kakao)

날짜만 입력하면 **AI가 국내 여행지 3곳을 추천**하고,
각 도시의 **맛집 정보까지 검색**해서 **여행 리포트를 자동으로 만들어주는** 프로그램입니다.

- 🤖 **Gemini API** : 날짜에 맞는 여행지 추천 + 리포트 작성
- 📍 **Kakao Local API** : 추천 도시의 맛집 검색

---

## ✨ 주요 기능

| 기능 | 설명 |
|------|------|
| 📅 날짜 입력 | 명령줄에서 `--date`로 여행 날짜 입력 (형식 자동 검증) |
| 🤖 여행지 추천 | Gemini가 날씨·행사·이유를 담아 국내 3곳 추천 |
| 📍 맛집 검색 | Kakao Local API로 도시별 맛집 최대 5곳 검색 |
| 📝 리포트 생성 | 추천 정보 + 맛집을 합쳐 Markdown 리포트 자동 작성 |
| 💾 결과 저장 | 리포트(.md) 3개 + 원본 데이터(.json) 1개 저장 |
| 🛡️ 에러 처리 | JSON 파싱 재시도, 맛집 검색 실패 시에도 중단 없이 진행 |

## 📊 결과물 설명

### 1) 여행 리포트 (`여행리포트_도시명_날짜.md`)

도시별로 하나씩, 총 **3개**가 생성됩니다.
각 리포트에는 다음 내용이 포함돼요.

- 📌 추천 지역 + 추천 이유 요약
- 🌤️ 날씨 요약
- 🎪 행사/축제 목록
- 🍽️ 맛집 리스트 (없으면 "데이터 없음")
- 🗓️ 1일 일정 제안 (오전 / 오후 / 저녁)

### 2) 원본 데이터 (`원본데이터_날짜.json`)

프로그램이 수집한 **모든 원본 데이터**를 담은 파일이에요.
나중에 데이터를 다시 활용하거나 분석할 때 유용합니다.

```json
{
  "date": "2025-05-10",
  "recommendations": [ ... ],       // AI가 추천한 도시 3곳 정보
  "restaurants_by_city": { ... },   // 도시별 맛집 검색 결과
  "errors": [ ... ]                 // 실행 중 발생한 오류 목록
}
```

### 1) 🌐 REST API의 요청/응답 구조와 HTTP 메서드 (GET/POST)

📌 REST API란?
REST API는 서버와 클라이언트가 정해진 규칙(HTTP)에 따라 데이터를 주고받는 방식입니다.

    API(Application Programming Interface): 프로그램끼리 소통하는 "창구"
    REST: 그 창구를 만드는 "설계 원칙"

📌 요청(Request)/응답(Response) 구조
요청(Request) 은 클라이언트 → 서버로 보내는 편지입니다.
- URL      : 어디로 보낼지 (예: https://api.example.com/users)
- Method   : 무엇을 할지 (GET, POST 등)
- Headers  : 부가 정보 (인증 토큰, 데이터 형식 등)
- Body     : 실제 데이터 (POST일 때 주로 사용)

응답(Response) 은 서버 → 클라이언트로 오는 답장입니다.
- Status Code : 결과 상태 (200 성공, 404 없음, 500 서버오류)
- Headers     : 부가 정보
- Body        : 실제 데이터 (보통 JSON)

📌 GET vs POST 차이
| 구분	| GET	| POST | 
|--------|------|----------------------|
| 목적	| 데이터 조회	| 데이터 생성/전송 |
| 데이터 위치	| URL에 포함 (쿼리스트링)	| Body에 포함 |
| 노출	| URL에 그대로 보임	| 상대적으로 안 보임 |
| 예시	| 검색, 목록 보기	| 회원가입, 글쓰기 |


| 메서드 | 용도 | 이 프로젝트에서의 예시 |
|--------|------|----------------------|
| **GET** | 데이터를 **조회**할 때 (주소창에 정보 담김) | Kakao 맛집 검색 (`?query=태안군 맛집`) |
| **POST** | 데이터를 **생성/전송**할 때 (본문에 정보 담김) | Gemini에게 프롬프트 전송 |

> 💡 **핵심**: GET은 "가져오기", POST는 "보내서 처리하기"로 이해하면 쉬워요.
> GET은 정보가 URL에 노출되지만, POST는 본문(body)에 담겨 더 많은 데이터를 안전하게 보낼 수 있습니다.

### 2) 🔗 LLM 출력을 JSON으로 구조화하여 다음 단계에 활용

📌 왜 JSON으로 구조화할까?
LLM(예: Gemini)은 기본적으로 자연어(문장) 로 답합니다. 그런데 이 답변을 다른 프로그램의 입력으로 쓰려면, 정해진 형식이 필요합니다. 그 형식이 바로 JSON입니다.

📌 흐름 예시 (여행 앱 시나리오)
1단계 - 사용자 입력:

"부산에서 바다 보이는 맛집 추천해줘"

2단계 - LLM이 JSON으로 출력:
{
  "city": "부산",
  "keyword": "바다 보이는 맛집",
  "category": "restaurant"
}

3단계 - 이 JSON을 지도/장소 검색 API의 입력으로 사용:
# LLM 결과(json 데이터)를 그대로 검색에 활용
result = map_api.search(
    query=llm_output["keyword"],
    region=llm_output["city"]
)

👉 핵심: 자연어 → 구조화된 데이터(JSON) → 다음 시스템 입력
이렇게 하면 "말"을 "기계가 바로 쓸 수 있는 데이터"로 바꿀 수 있습니다.

### 3) 🛡️ 외부 API 호출의 대표 오류와 대응 원칙

외부 API를 호출할 때는 다양한 오류가 발생할 수 있고, 각각 대응 방법이 다릅니다.

| 오류 종류 | 원인 | 대응 원칙 |
|-----------|------|-----------|
| **인증(Auth) 오류** (401) | API 키가 없거나 틀림 | 키가 올바른지, `.env`에 잘 로드됐는지 확인 |
| **쿼터(Quota) 초과** (429) | 무료 사용량/호출 한도 초과 | 잠시 대기 후 재시도, 호출 횟수 줄이기 |
| **네트워크 오류** | 인터넷 끊김, 서버 응답 없음 | `try-except`로 감싸고 재시도 로직 적용 |
| **파싱(Parsing) 오류** | 응답이 예상한 JSON 형식이 아님 | 재시도(최대 1회) + 실패 시 "데이터 없음" 처리 |

📌 코드 예시 (오류 대응)
import requests

try:
    response = requests.get(url, timeout=5)   # 네트워크: 타임아웃 설정
    response.raise_for_status()               # 인증/쿼터: 상태코드 확인
    data = response.json()                     # 파싱: JSON 변환 시도
except requests.exceptions.Timeout:
    print("네트워크 오류: 시간 초과")
except requests.exceptions.HTTPError as e:
    print(f"HTTP 오류: {e}")                   # 401, 429 등
except ValueError:
    print("파싱 오류: JSON 형식이 아님")

👉 대응 원칙 요약: "오류가 날 수 있다고 가정하고, 미리 예외처리를 해둔다!"

> 💡 **핵심**: 외부 API는 **언제든 실패할 수 있다고 가정**하고 코드를 짜야 합니다.
> 이 프로젝트에서는 **JSON 파싱 재시도**와 **맛집 검색 실패 시에도 중단 없이 진행**하도록 처리했습니다.

### 4) 🔑 API 키를 .env/환경변수로 관리하는 이유

API 키를 **코드에 직접 작성하면 안 되는 이유**가 있습니다.

```python
# ❌ 나쁜 예시 (코드에 키를 직접 작성)
GEMINI_API_KEY = "AIzaSyABC123실제키노출..."

# ✅ 좋은 예시 (.env에서 불러오기)
from dotenv import load_dotenv
import os
load_dotenv()
GEMINI_API_KEY = os.getenv("GEMINI_API_KEY")
```

| 이유 | 설명 |
|------|------|
| 🔒 **보안** | 코드를 GitHub에 올리면 키가 그대로 노출 → 악용될 수 있음 |
| 💸 **비용 보호** | 노출된 키로 타인이 API를 쓰면 **요금 폭탄** 위험 |
| 🔄 **관리 편의** | 키가 바뀌어도 `.env`만 수정하면 됨 (코드 수정 불필요) |
| 👥 **협업** | 각자 자신의 `.env`를 사용 → 키 공유 없이 협업 가능 |

> 💡 **핵심**: `.env`는 `.gitignore`에 추가해서 **절대 외부에 공유되지 않도록** 합니다.
> 키는 "비밀번호"라고 생각하면 이해하기 쉬워요! 🔐
